# jelly-flow 인계

## 목표와 확정 범위

사용자가 Jelly fork 프로젝트를 `jelly-flow`라는 이름으로 만들었다고 알렸다.
목적은 **실제 TypeScript 애플리케이션의 함수 호출 관계 분석 개선**이다.
React 전용 제품이나 DART 전용 분석기가 목적은 아니다. DART를 첫 검증 대상으로 쓰며
React callback은 현재 확인된 우선 문제다. Electron IPC는 독립적인 후속 확장 후보이고,
DART 전용 규칙의 필요성은 아직 입증되지 않았다.

사용자는 이 프로젝트에서 이어갈 작업을 정리한 handoff를 요청했다. 현재 세션에서는
fork 수정·원격 발행을 하지 않았다. jelly-flow의 URL, 로컬 경로, upstream revision은
제공받거나 확인하지 못했다. 다음 세션에서 대상 저장소와 자체 AGENTS/개발 지침을 먼저
확인하고 설치된 fork 버전을 기록한다. 이전 DART 경로에서 계속 production edits하지 않는다.

초기 성공 기준: 작은 재현 예제와 DART의 실제 callback 경로에서 연결률이 개선되고,
알려진 오연결이 늘지 않으며, 해석하지 못한 관계와 분석 범위가 명시되어야 한다.
범용·완전한 JS/TS 그래프를 보장하는 프로젝트로 범위를 확대하지 않는다.

## 확인한 결과

LSP: typescript-language-server 4.3.4 및 6.0.1을 stdio로 실제 실행했다.
둘 다 DART의 TypeScript tsserver 5.3.3을 명시 사용했고 버전 알림을 검증했다.
최소 예제 10위치 + DART 5위치의 results JSON은 양 서버에서 동일했다.
직접 호출/별칭/재수출/동명 메서드는 연결했지만, 인자 callback과 useCallback 반환 호출은
놓쳤다. DART closeViewInstance 변수의 prepareCallHierarchy는 빈 배열이었다.
일부 callback 본문 호출은 바깥 hook에 귀속됐다. 다른 TS 엔진 버전은 검증하지 않았다.

Jelly 평가: npm `@cs-au-dk/jelly@0.13.0`, Node 24.20.0, Windows,
실제 React/ReactDOM 18.3.1. 정적 분석만 사용; approximate interpretation/동적 실행 없음.

| 사례 | 관측 |
|---|---|
| LSP와 동일한 최소 fixture | 선택한 기대 연결 8/8 존재: 별칭, 재수출, A/B 메서드, 인자 callback, 반환 callback, 본문, Map |
| 실제 React+ReactDOM fixture | onClick → useCallback arrow → persist 연결 성공 |
| `--no-callgraph-external` | 위 React 두 연결 유지. 다른 heuristic까지 모두 제거된 결과라는 뜻은 아님 |
| Map 상수 키 음성 대조군 | saveOnly → remove / removeOnly → save의 오연결 2개 존재 |
| 무관 함수 | fixture의 neverCalled/unrelated incoming 0 |
| DART hook 단독 entry | closeViewInstance callback의 내부 두 호출은 존재, incoming 0 |
| DART renderer main.tsx entry | wall 92.562초, exit 134, 4096MB old-space 한도에서 heap OOM; graph/diagnostics 생성 실패 |

완료 분석의 Jelly 시간/메모리(--gc 없음, OS peak RSS 아님):
baseline 79ms/48MB, negative 44ms/46MB, React 11.504s/1034MB,
React no-external 10.638s/1022MB, DART hook 17.219s/998MB.
후자는 1130 modules/5553 functions, errors 0/warnings 1055였다.
warnings에는 dynamic property read 604건, object spread 140건 등이 있다.
`--obj-spread` 및 다른 옵션은 아직 비교하지 않았다.
5개 완료 분석은 timeout=false/aborted=false/unprocessedTokens=0이었다.
정상 종료·errors 0은 정확성/완전성 증명이 아니다. raw graph에는 module-loading 등도
포함되어 diagnostics의 함수 연결 수와 다를 수 있다.

진입점/실제 의존성 경로에 주의: 최초 worktree basedir는 junction 바깥 React를 제외했다.
그 결과는 excluded-dependencies/에 보존하고 최종 React 근거에서 제외했다.
이후 common ancestor를 basedir로 주고 명시한 entry의 import만 따라 분석했다.
완료한 hook graph 파일은 평가 worktree 소스 또는 node_modules였다.
분석 base 확대는 사용자 디렉터리 전체 순회가 아니다.
전체 renderer 실패로 'React 문맥 부족이 DART incoming 누락의 원인'이라는 가설은 미확정이다.

## 확인한 수정 지점

Jelly 0.13.0 `lib/natives/ecmascript.js`의 Map 모델:
set은 값들을 MAP_VALUES에 합치고 get은 키를 구분하지 않고 MAP_VALUES를 반환한다.
상수 키 대조군의 오연결과 일치한다. fork source의 해당 구현을 다시 확인한다.
upstream `src/natives/nativebuilder.ts`에는 함수 모델/solver 제약을 정의하는 내부 구조가 있다.
외부 라이브러리를 간단히 꽂을 수 있는 공식 plugin Interface가 확인된 것은 아니다.
웹 master와 평가 npm 버전이 다를 수 있으므로 fork baseline을 고정한다.

## 다음 작업 — 순서대로

1. **fork 기준 확립과 기존 결과 재현**
   - jelly-flow 로컬 경로/remote/upstream SHA/라이선스 고지/개발 명령 확인.
   - 평가 fixtures를 fork 테스트 관례에 맞춰 이식. 테스트 기대값은 알려진 실제 연결과
     금지 연결로 작성하고, 현재 누락/오연결은 RED 또는 명시적 baseline으로 남긴다.
   - 원본 solver/model의 책임과 호출 경로를 확인한 뒤 변경한다.

2. **React 반환 callback의 제한된 모델 시제품**
   - React import binding과 버전을 확인해 useCallback 인자 함수와 반환 함수 값을 연결한다.
     같은 이름의 사용자 함수나 다른 패키지에는 규칙을 적용하지 않는다.
   - useCallback 자체가 callback을 실행하는 것으로 연결하지 않는다.
   - React/ReactDOM 구현 분석을 요약 모델로 대체할 수 있는지 확인한다.
     단순히 의존성을 제외하고 미해결을 숨기는 방식을 쓰지 않는다.
   - 별칭/재수출/namespace import, custom hook 반환, 실제 DART closeViewInstance 호출부,
     무관 함수 음성 대조군을 검증한다. JSX prop 전달과 이벤트 실행은 별도 관계로 구분한다.

3. **상수 Map 키 정밀도 개선을 독립 slice로 검토**
   - 'save'/'remove' 키를 분리하는 최소 개선과 회귀 테스트.
   - 미지 키·복수 write·재할당·delete/clear 처리 범위를 명시한다.
   - 알 수 없는 키를 무시해 누락을 만드는 것보다 가능한 관계/미해결을 표시한다.
     모든 동적 Map 동작을 완벽히 지원하려고 범위를 확대하지 않는다.

4. **DART 비용/누락 비교**
   - 같은 source snapshot/entry/dependency 범위로 원본과 fork 비교.
   - hook 범위부터 시작, 이후 renderer. 초기 예산은 평가와 같은 90초 분석/4GB heap/
     120초 외부 deadline. 실패를 그래프 완료로 표시하지 않는다.
   - model 적용 대상/제외 대상/지원하지 않는 callback 및 경고를 보고한다.
   - renderer OOM의 원인은 아직 profile하지 않았다. 라이브러리 요약으로 해결되는지
     확인하기 전 solver 재작성이나 단순 heap 증설을 해답으로 정하지 않는다.

5. **수집기 통합은 별도 후속 단계**
   - 정적 호출, 모델로 추론한 관계, 등록/전달, 미해결을 구분할 출력 계약 검토.
   - DART architecture-evidence 연결은 개선 효과가 입증된 후 별도 작업으로 진행.
     이전 unavailable 36개/prior comparison 진단이 자동 해소된다고 주장하지 않는다.
   - Electron IPC는 후속 선택 범위. DART-specific 규칙은 실제 미해결 사례가 있을 때만.

## 성공/중단 기준과 검증

우선 성공은 React fixture와 DART 실제 callback 호출자 연결의 개선, 음성 대조군 유지,
같은 조건의 비용 기록이다. Map 개선은 오연결 두 개 제거와 올바른 두 개 유지로 검증한다.
스캔 누락을 0으로 채우거나 테스트를 결과에 맞춰 약화하지 않는다.
분석 완전성이 확인되지 않으면 bounded/partial 결과로 표시한다.

상태 오너/solver 의미론 변경, 대규모 컨텍스트 민감 분석, 프로젝트 전체 수집 범위 변경이
필요해지면 범위를 다시 설계한다. 성공을 위해 제한 없이 모델/heap/예산을 늘리지 않는다.
CodeQL은 사용자 제약으로 후보에서 제외됐다. 제거된 CodeGraph를 복구하지 않는다.

이미 실행한 검증: 위 실제 Jelly CLI 실행, LSP 실질의, JSON에서 선택 edge 원문 대조,
runner/summarizer `node --check`, `git diff --check`. 앱 변경이 없어 앱 E2E는 실행 안 함.
앞으로 필요한 검증: fork baseline 재현 → 초점 테스트 RED/GREEN → upstream 영향 테스트 →
동일 DART entry A/B 비용/정확성 비교. 일반 단위 테스트 통과를 실제 DART 성공으로 대체하지 않는다.

적용할 스킬은 jelly-flow에서 사용 가능한 것을 우선한다. 비-UI 분석 동작은 `tdd`,
원인 확인이 필요하면 `diagnose`, 요청/프로젝트 규칙에 따라 `git-review-commit`.
스킬 실행을 위해 별도 에이전트를 자동 생성하지 않는다. DART 규칙을 fork에 무조건 복사하지 않는다.
